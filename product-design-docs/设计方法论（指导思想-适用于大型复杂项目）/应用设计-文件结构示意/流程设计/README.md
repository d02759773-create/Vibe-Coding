# 流程设计

本目录存放应用层的流程设计，是将业务流程「翻译」为系统交互步骤的关键产出物。这里的流程关注**系统行为**，而非业务现实。

---

## 应该放什么

### 1. 状态机文档（核心）
- 各单据/对象的**状态定义**：每个状态的含义是什么、进入条件、退出条件
- **状态流转规则**：从哪个状态可以流转到哪个状态，触发条件是什么
- **关闭规则**：业务单关闭三态、通知单执行结果、结果单红冲/修正规则
- **取消规则**：哪些状态可以取消，取消后联动影响什么

### 2. 系统交互流程图
- 用户点了什么操作 → 系统触发了什么动作
- 细化到可编码粒度（每个步骤对应一个系统行为）

### 3. 时序图
- 跨系统/跨模块的交互时序（如 ERP ↔ WMS、ERP ↔ POS）
- 使用 Mermaid sequenceDiagram 绘制

## 不应该放什么

| 内容 | 应该放哪里 |
| --- | --- |
| 业务现实（人做了什么） | 业务设计/流程模型/ |
| 字段级别的校验规则 | PRD |
| 界面原型和交互规范 | 界面设计/ |

## ERP 三层单据状态口径（特定场景示例）

> [!NOTE]
> 以下三层单据模型仅适用于**采购/销售/配销等存在"业务单→通知单→结果单"链路的 ERP 系统**。非此类项目（如 CMS、数据分析平台、营销工具等）可以跳过本节，直接参考上方的通用状态机模板。

涉及标准采购、销售、配销等三层单据链路时，必须先对齐项目全局三层单据规则，再写具体状态机。

| 单据层级 | 状态口径 | 说明 |
| --- | --- | --- |
| L1 业务单 | 审核/业务状态 + 关闭状态：未关闭 / 关闭中 / 已关闭 | "关闭中"表示已放弃剩余可下推量，但仍等待在途 L2 收尾 |
| L2 通知单 | 推送状态 + 执行状态 | 无 L2 审核态、无 L2 关闭状态、无旧四维模型 |
| L3 结果单 | 结果凭证状态 + 红冲/修正状态 | L3 是业务事实凭证，不承担继续下推 |

> [!IMPORTANT]
> 不得沿用旧模型里的"单据状态 + 推送下游状态 + 下游作业状态 + 关闭状态"四维状态；如果历史文档已有该写法，应在重写状态机时收敛为 L2 推送状态 + 执行状态。

### L2 通知单推荐模板

| 维度 | 推荐枚举 | 说明 |
| --- | --- | --- |
| 推送状态 | 待推送 / 推送中 / 推送成功 / 推送失败 / 取消中 / 已取消 / 无需推送 | 描述通知单与下游系统的推送关系 |
| 执行状态 | 待执行 / 执行中 / 全量完成 / 缺量完成 / 执行失败 / 已取消 | 描述下游或系统自身执行结果 |

模块有特殊状态时，可以扩展，但必须说明为什么全局枚举不足，并在字段清单和 PRD 中同步。

## 与业务设计/流程模型的区别

| 维度 | 业务设计/流程模型 | 应用设计/流程设计 |
| --- | --- | --- |
| 视角 | 业务现实（人做了什么） | 系统行为（用户点了什么、系统怎么响应） |
| 粒度 | 业务步骤级 | 可编码粒度 |
| 包含异常？ | 是（业务异常） | 是（系统异常+业务异常） |
| 读者 | 业务方、产品 | 产品、研发、测试 |

## 状态机文档模板（通用）

以下为通用状态机模板，适用于各类系统的单据或对象：

```markdown
# [单据名称]状态机

## 一、状态定义

| 状态值 | 显示名称 | 含义 | 进入条件 | 退出条件 |
| --- | --- | --- | --- | --- |
| `draft` | 待提交 | 单据已创建，未提交审核 | 人工创建 / 系统生成 | 提交或删除 |
| `pending` | 待审核 | 已提交，等待审核 | 点击「提交」 | 审核通过 / 退回 / 取消 |
| `approved` | 已审核 | 审核通过 | 审核通过 | 下推执行 / 取消 |
| `cancelled` | 已取消 | 单据作废 | 在允许取消的状态下操作 | — |

## 二、状态流转图

\`\`\`mermaid
stateDiagram-v2
    [*] --> 待提交 : 创建
    待提交 --> 待审核 : 提交
    待审核 --> 已审核 : 审核通过
    待审核 --> 待提交 : 退回
    待审核 --> 已取消 : 取消
    待提交 --> 已取消 : 删除草稿
    已审核 --> [*]
\`\`\`

## 三、操作权限矩阵

| 操作 | 待提交 | 待审核 | 已审核 | 已取消 |
| --- | --- | --- | --- | --- |
| 编辑 | ✅ | ❌ | ❌ | ❌ |
| 提交 | ✅ | ❌ | ❌ | ❌ |
| 退回 | ❌ | ✅ | ❌ | ❌ |
| 取消 | ✅ | ✅ | ❌ | ❌ |
| 下推执行 | ❌ | ❌ | ✅ | ❌ |
| 查看 | ✅ | ✅ | ✅ | ✅ |

## 四、逆向操作规则

| 逆向操作 | 允许的状态 | 触发条件 | 后果 |
| --- | --- | --- | --- |
| 取消 | 待提交、待审核 | 操作人必须是创建人或主管 | 单据作废，释放关联资源 |
| 撤回 | 待审核 | 操作人是提交人 | 回退到待提交，可修改 |

## 五、关闭/完结规则（如适用）

| 关闭类型 | 触发条件 | 状态变化 | 后续操作限制 |
| --- | --- | --- | --- |
| 正常完结 | 全部后续操作执行完成 | → 已关闭 | 不允许任何修改 |
| 强制关闭 | 人工决定不再继续 | → 已关闭 | 不允许修改，但保留审计记录 |
```

## 场景示例：ERP 三层单据状态模型

```markdown
# [单据名称]状态机

## 一、状态定义

| 状态值 | 显示名称 | 含义 | 进入条件 |

| `draft` | 待提交 | 单据已创建，未提交审核 | 人工创建 / 系统生成 |
| `pending` | 待审核 | 已提交，等待审核 | 点击「提交」 |
| `approved` | 已审核 | 审核通过 | 人工审核通过 / 自动审核 |
| `cancelled` | 已取消 | 单据作废 | 在允许取消的状态下操作 |

## 二、状态流转图

    待提交 --> 待审核 : 提交
    待审核 --> 已审核 : 审核通过
    待审核 --> 待提交 : 退回
    待审核 --> 已取消 : 取消
    已审核 --> [*]
\`\`\`

## 三、操作权限矩阵

| 操作 | 待提交 | 待审核 | 已审核 | 已取消 |
| --- | --- | --- | --- | --- |
| 编辑 | ✅ | ❌ | ❌ | ❌ |
| 提交 | ✅ | ❌ | ❌ | ❌ |
| 取消 | ✅ | ✅ | ❌ | ❌ |

## 四、关闭规则（如适用）

- **业务单关闭中**：[触发条件] → 放弃剩余可下推量，等待在途通知单执行完成
- **业务单已关闭**：[触发条件] → 所有在途通知单收尾，业务单完结
- **通知单执行完成**：[触发条件] → 形成全量完成或缺量完成，不再接受二次有效回传
```

## 状态机验收清单

| 检查项 | 要求 |
| --- | --- |
| 状态来源 | 枚举与全局规范、字段清单、业务 PRD 一致 |
| 触发条件 | 每个状态变化都有明确触发动作或系统事件 |
| 逆向操作 | 取消、撤回、关闭、红冲、重推、补偿都有边界 |
| 缺量场景 | 缺量完成后差额不回补，补货须新开业务订单 |
| 二次回传 | L2→L3 只接受一次有效回传，重复回传按幂等/拒绝处理 |
| 页面操作 | 状态机能推导列表行操作和详情操作区，不出现无来源按钮 |
