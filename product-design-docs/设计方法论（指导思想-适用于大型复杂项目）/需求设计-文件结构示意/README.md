# 建议的文件结构（参考）

> 本目录是**需求设计层的模板参考**，供 AI 和团队成员学习、参照使用。
> 实际使用时，每一期项目单独建立文件夹（如「物料二期/」），在其中参照本模板创建对应文档。

---

## 定位与执行顺序

需求设计回答"做什么、不做什么、优先级是什么"，是后续业务设计、应用设计和 PRD 的范围基线。

但需求设计不应脱离业务现状独立启动。正确顺序是：

```
业务现状预梳理 → 需求调研 → 需求规格说明书 → 功能需求一览表
                        │
                        └── 业务设计 / 应用设计发现问题后，反向修正需求基线
```

> [!IMPORTANT]
> 如果业务设计或应用设计阶段发现范围、规则、状态闭环存在问题，必须回写需求规格说明书和功能需求一览表；不能只在后续文档里局部修正。

## 产出物结构

需求设计阶段有 3 个核心产出物，对应本目录的 3 个子文件夹：

```
建议的文件结构（参考）/
├── 1. 需求调研报告/        ← 过程性档案：记录调研活动和原始素材
├── 2. 需求规格说明书/      ← 核心交付物：结构化的需求基线（回答"做什么"）
└── 3. 业务功能需求一览表/  ← 管理工具：功能清单 + 优先级 + 状态追踪
```

> [!NOTE]
> 需求规格说明书中只包含宏观的泳道级业务流程概述。详细的流程推演（步骤级+异常分支）在业务设计的流程模型中展开；系统级的状态机和交互流程在应用设计的流程设计中展开。三者是递进关系。

---

## 三个产出物的关系

```
需求调研报告  ──→  需求规格说明书  ──→  业务/功能需求一览表
（原始素材）       （结构化基线）         （功能清单的表格形式）
                         │
                         └──→ 业务设计 / 应用设计 / PRD
```

| 产出物 | 性质 | 核心问题 | 主要读者 |
| --- | --- | --- | --- |
| **需求调研报告** | 过程档案 | 我们调研了什么、发现了什么 | 项目组内部存档 |
| **需求规格说明书** | 基线文档 | 做什么、不做什么、范围边界 | 业务方、产品、管理层 |
| **业务/功能需求一览表** | 管理工具 | 哪些功能、优先级如何、进展怎样 | 产品、开发、测试、管理层 |

## 不应该放什么

| 内容 | 应该放哪里 | 原因 |
| --- | --- | --- |
| 字段定义、字段枚举、必填性、控件类型 | PRD 文档集的字段清单 | 字段清单是字段 SST |
| 详细状态机、操作权限矩阵 | 应用设计/流程设计 或业务 PRD | 需求层只需要说明功能范围和关键约束 |
| 取消/关闭/红冲的完整推演 | 业务设计/流程模型 或 PRD 流程推演 | 需求层只记录需要覆盖这些能力，不展开全链路 |
| REST 路径、DDL、索引、错误码 | 技术设计 | PM 需求基线不写技术实现 |
| Demo 页面布局、表格列宽、Mock 数据 | Demo PRD / 前端原型 | 防止需求层反向污染页面设计 |

## 阶段门禁

进入业务设计前，至少确认以下内容：

| 检查项 | 要求 |
| --- | --- |
| 业务范围 | 覆盖场景、业务主体、外部系统、Out of Scope 已明确 |
| 优先级 | P0/P1/P2 或高/中/低有业务依据 |
| 功能边界 | 每个功能点有唯一编号，可追溯到后续设计、开发、测试 |
| 待确认事项 | 未决问题集中记录，不能散落在正文中 |
| 旧稿状态 | 历史资料须标注"历史稿 / 已废止 / 仅供溯源"，避免 AI 当作新规则 |
