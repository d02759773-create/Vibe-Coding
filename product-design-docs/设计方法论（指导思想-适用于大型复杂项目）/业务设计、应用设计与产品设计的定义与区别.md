# 业务设计、应用设计与产品设计的定义与区别

> **参考来源**：《大话软件工程——需求分析与软件设计》（作者：李鸿君）  
> **文档定位**：本文是对书中核心方法论的结构化整理，适用于产品经理、需求分析师理解各设计阶段的职责与产出，也作为后续 AI 协作的背景知识。  
> **核心观点**：产品经理在中后台/ERP 系统建设中，有三层核心设计工作需要亲自主导——需求设计、业务设计、应用设计；"产品设计"是更宏观的整合视角，贯穿始终，不是一个独立的执行阶段。

---

## 一、软件工程设计的整体分层

一套完整的中后台系统从 0 到 1，涉及以下几个设计层次。它们在交付物上有先后关系，但在真实项目中不是一次性瀑布，而是带回写的迭代闭环：

```
业务现状预梳理 → 需求设计 → 业务设计 → 应用设计 → PRD → 技术设计 → 开发 → 测试 → 部署
      ↑             │          │          │
      └─────────────┴──────────┴──────────┘
                 评审发现问题后，回写需求范围、业务规则或应用机制
```

**《大话软件工程》的核心贡献**，是在传统"需求→技术设计→开发"的流程中，明确引入了**业务设计**和**应用设计**两个中间层，填补了"需求写完但研发不知道怎么建系统"的核心断层。

> [!NOTE]
> **什么时候需要三层设计？** 并非所有项目都需要完整的业务设计 + 应用设计。以下判断标准供参考：
> - **三层全开**：业务规则复杂、多角色多系统协作、存在大量异常/逆向/红冲逻辑的后台系统（如 ERP、供应链、交易中心）；团队 ≥ 5 人，交付周期 ≥ 3 个月。
> - **跳过业务设计**：业务规则简单、流程标准化程度高（如 CMS、简单 CRUD 后台）；业务方的诉求就是"照旧系统做一版"，没有流程优化空间。
> - **跳过应用设计**：有成熟的设计系统且交互模式高度标准化（如内部工具、标准列表-详情型后台）；或者应用设计的内容可以由前端架构师在技术设计阶段覆盖。
> - **只做需求设计 + PRD**：小型工具、内部脚本、一次性数据分析平台等。此时需求规格说明书直接作为 PRD 的需求章节，不再单独走业务设计和应用设计流程。
>
> 核心判断标准：**如果一个需求可以通过"照旧系统"或"列表+详情+表单"说清楚，就不需要三层设计**。三层设计的价值在于处理那些"说不清楚、画不明白、需要多方对齐"的复杂场景。

> [!IMPORTANT]
> **执行顺序的正确理解**：先做必要的业务现状预梳理，再冻结需求基线；需求基线冻结后，再进入更细的业务流程推演和应用机制设计。若业务设计或应用设计发现需求范围、业务规则、状态闭环有问题，必须反向更新需求基线和功能清单，而不是让后续文档各自带着不同口径继续推进。

**产品经理的职责边界**：

| 阶段 | 主导者 | 说明 |
| --- | --- | --- |
| **需求设计** | 产品经理 | 把用户诉求转化为可开发的需求基线 |
| **业务设计** | 产品经理 | 决定系统怎样才能真正解决业务痛点 |
| **应用设计** | 产品经理 | 将业务逻辑转换为系统可实现的方案 |
| 技术设计 | 研发/架构师 | 产品经理配合确认可行性 |
| **PRD** | 产品经理 | 综合三层设计产出，形成面向研发/测试的可交付文档 |

## 二、三层核心设计详解（产品经理主导）

### 2.1 需求设计（Requirement Design）

**定义**：把"用户想要什么"转化为可检验、可开发的《需求规格说明书》的全过程，包含调研与分析两大环节。

**关注点**：系统必须做什么（What）；强调**需求的完整性与正确性**

#### 主要工作

**第一步：调研**
- 访谈决策层、管理层、一线用户，绘制现状图、整理既有表单
- 常用手段：访谈、问卷、观察、竞品分析、现状梳理
- 产出：《现状构成图》《访谈记录》《既存表单》

**第二步：分析**
- 对原始需求去粗取精，划分为目标需求、业务需求、功能需求三层
- 验证需求一致性与可行性，消除重复与冲突
- 用用例、场景、表格等形式固化功能与非功能需求

**第三步：规格化**
- 编写《需求规格说明书》，获得业务方、技术方、测试方的共同评审和签字确认

#### 典型方法论

| 方法 | 用于 |
| --- | --- |
| 5W1H / 6W2H | 梳理需求背景与场景 |
| Kano 模型 / 需求四象限 | 优先级排序 |
| 用例驱动 / 场景驱动 | 细化功能需求 |
| 原型/线框图 | 辅助需求确认 |

#### 需求设计的结构化输出维度

需求设计处于"需求分析完成"到"概要设计开始"之间，核心任务是把需求从多个维度细化并结构化，为后续设计提供输入基础：

| 维度 | 核心任务 | 典型交付物 |
| --- | --- | --- |
| **功能维度** | 继承功能需求一览，细化功能点的触发条件、输入/输出、优先级和分期排期 | 《业务/功能需求一览表》 |
| **流程与规则维度** | 描述业务流程（泳道图）及对应规则，用于指导系统实现和工作量估算 | 《业务流程概要说明》 |
| **数据与架构维度** | 从业务架构、数据架构角度对需求进行映射，为后续系统架构设计提供依据 | 业务架构图、概念数据关系图 |

> [!NOTE]
> **与业务设计的分工**：需求设计中的业务流程概要（泳道级宏观描述）与业务设计中的流程模型（步骤级+异常分支推演）是递进关系，不是重复。

#### 标准化交付物清单

> 以下为需求设计的核心交付物。其中"业务流程概要说明"是泳道级宏观描述，后续业务设计和应用设计中的流程模型和流程设计是在此基础上逐步细化的递进关系，不是重复。

| 文档名称 | 说明 |
| --- | --- |
| **《需求规格说明书》** | 综合说明书，覆盖目标、业务、功能三层需求，是后续所有设计的基线文档 |
| **《业务/功能需求一览表》** | 功能点清单，含优先级、分期、触发条件，是需求到开发全周期的追踪工具 |
| **《业务流程概要说明》** | 泳道级流程图+规则概要，描述主要业务路径（宏观级，不展开异常分支），为业务设计的详细流程推演提供起点 |

这些文档既是后续设计、开发、测试的输入，也是项目验收与评估的依据。

#### 产品经理的核心职责

1. 定义调研范围与指标，组织访谈与问卷
2. 按"目标→业务→功能"三层结构梳理需求并排序
3. 从功能、流程、价值、数据四个维度对需求进行结构化
4. 牵头编写和评审《需求规格说明书》，确保研发、测试、实施都能据此工作

### 2.2 业务设计（Business Design）

**定义**：基于需求设计成果，从业务方视角出发，对业务流程、功能和数据进行梳理与优化，决定系统怎样才能真正解决业务痛点，最大化业务价值。

**关注点**：业务功能、业务逻辑、业务数据；强调**业务正确性**

**核心问题**：客户现在是怎么做业务的？哪些地方需要优化？系统建成后业务流程是什么样的？

> [!IMPORTANT]
> **书中的重要修正**：业务设计应先于需求设计进行，指的是在冻结需求基线之前，必须先理解业务现状和业务流程，再据此提出信息化需求，避免"照着旧系统抄"的陷阱。进入正式交付后，需求设计提供范围和优先级约束，业务设计继续深化流程、规则和异常分支，两者是前置理解 + 后续深化的关系，不是互相替代。

#### 主要工作

| 维度 | 内容 |
| --- | --- |
| **架构层** | 梳理并优化业务流程，形成业务架构（组织、流程、权限模型） |
| **功能层** | 把需求中的功能细化为「活动、字典、看板、表单」等形式，确认交互与数据逻辑 |
| **数据层** | 定义数据标准、数据责任与数据质量规则 |

#### 产出物

- 业务架构图、流程模型、数据模型
- 业务功能一览表
- 业务用例、数据字典

#### 产品经理的核心职责

- 参与业务流程梳理，确保功能与流程匹配业务人员工作习惯
- 验证功能粒度与业务场景，防止"只知其然不知其所以然"
- 与研发共同确定数据标准，避免信息孤岛

---

### 2.3 应用设计（Application Design）

**定义**：把业务设计成果转换为系统实际能做到的应用方案，让最终用户感受到系统价值；关注"系统好不好用、能不能快速响应变化"，是业务设计与技术设计之间的桥梁。

**关注点**：界面、交互、模块化组件、系统机制；强调**易用性与应变性**

**核心方法**：采用"**组件 + 机制**"思维——将业务功能拆分为可复用的组件，用流程、规则、配置等机制支撑业务逻辑，构建灵活可配置的系统架构。

#### 主要工作

| 维度 | 内容 |
| --- | --- |
| **架构与流程** | 细化架构图和流程分解图，分解到可编码粒度 |
| **机制设计** | 随需应变机制、配置管理、日志与监控等系统机制设计 |
| **界面与交互** | 输出界面原型和交互规范，确保与设计系统一致 |

#### 产出物

- 应用架构图、流程分解图
- 系统机制说明书
- 高保真界面原型、交互规范
- 应用系统用例

#### 产品经理的核心职责

- 主导体验与交互方案评审，确保设计符合目标用户场景
- 验证可配置性、可扩展性，为后续版本迭代留下空间
- 与研发共同确认接口和数据契约，减少集成风险

> [!IMPORTANT]
> **应用设计 ≠ 单纯的画原型**：它的核心价值是把业务逻辑转换为系统能实现的应用机制，重点是"组件化和灵活应变"，原型只是其中一个产出物。

---

### 2.4 技术设计（Technical Design）——研发主导，产品配合

**定义**：把应用设计成果转化为开发团队可直接实现的技术方案，由架构师/研发主导，产品经理配合确认可行性与业务约束。

**核心产出物**：

| 产出物 | 说明 |
| --- | --- |
| **技术架构说明书** | 系统整体技术架构、组件划分、调用关系、部署方式 |
| **数据接口规范/数据字典** | 各模块之间的数据格式与接口契约 |
| **部署手册** | 部署环境、安装步骤、回滚方案 |
| **测试计划** | 功能、性能、安全等维度的测试策略与用例 |
| **用户手册** | 面向最终用户的功能说明与使用流程 |
| **系统机制说明书** | 配置管理、日志、监控、安全控制的技术级说明 |
| **非功能性需求落实文档** | 响应时间、并发量、安全合规等技术实现方案 |

**三层技术设计成果**（细化到可编码粒度）：

- **应用界面层**：界面原型、交互流程、UI 组件规范
- **业务逻辑层**：业务规则、流程引擎配置、数据处理与校验逻辑
- **数据访问层**：数据库表结构、索引、视图、数据同步与备份策略

## 三、关于"产品设计"与 PRD 的位置

### 3.1 产品设计是什么

产品设计（Product Design）是一个**比需求/业务/应用设计更宏观的视角**，而不是一个独立的执行阶段。它不具有固定的工作流程，更多是一种**资源整合与信息整合**的能力：

- 从市场和用户角度定义"产品是什么、解决什么问题、以什么模式交付"
- 贯穿需求设计、业务设计、应用设计全程，持续对齐商业目标与用户价值

可以理解为：**产品经理做需求设计 + 业务设计 + 应用设计，输出的总和就是产品设计的结果**。产品设计是"角色视角"，不是"流程节点"。

### 3.2 PRD 的位置与定位

PRD（产品需求文档）是三层设计完成后的**综合交付物**，面向研发和测试，而不是某一个设计阶段的内部产出：

- **内容来源**：综合需求设计的功能范围、业务设计的业务规则、应用设计的交互与数据模型
- **面向读者**：研发工程师、测试工程师、项目实施人员
- **本质定位**：把三层设计成果"编译"成一份可执行的施工说明书

> PRD 与三层设计的关系，类比"蓝图"与"施工说明书"——设计阶段产出蓝图，PRD 是给施工队看的整合版本，二者性质不同，不能互相替代。

**PRD 应独立存放于顶层目录，与需求设计、业务设计、应用设计平级**，而不是某一层设计的子目录。

> [!NOTE]
> **业务 PRD 与 Demo PRD 的区别**：三层设计完成后，实际输出两种 PRD：
> - **业务 PRD**：面向研发和测试，包含完整的字段清单、状态机、业务规则、异常处理和验收标准。它是三层设计的正式综合交付物。
> - **Demo PRD**：面向前端开发和 UI 实现，专注页面布局、控件类型、交互反馈和 Mock 数据展示。它是业务 PRD 中界面相关内容的可视化落地版本。
>
> 两者关系：业务 PRD 是权威源，Demo PRD 是业务 PRD 中界面和交互部分的工程化展开。Demo PRD 不能反向修改业务规则，字段定义以业务 PRD 的字段清单为准。

### 3.3 权威源矩阵（SST）

分层文档能成立的前提，是每类信息只能有一个权威来源。其他文档可以引用、转写或展开，但不能重新定义同一口径。

| 信息类型 | 权威来源 | 其他文档怎么用 | 禁止事项 |
| --- | --- | --- | --- |
| 项目范围、目标、优先级 | 需求规格说明书 + 业务/功能需求一览表 | 业务设计、应用设计、PRD 按此控制范围 | 后续文档自行新增 P0 功能 |
| 业务规则、异常分支、取消/关闭/红冲语义 | 业务设计流程模型 / 正式流程推演 / 业务主 PRD | 应用设计和 Demo PRD 转译为系统动作 | 在页面稿里重新发明业务规则 |
| 业务实体、业务关系、业务术语 | 业务设计 / 数据设计 | 字段清单和 PRD 引用业务概念 | 把数据库表结构写入业务设计 |
| 字段定义、字段枚举、必填性、展示范围 | 字段清单 | 业务 PRD 与 Demo PRD 只引用字段名和规则 | 在业务 PRD、Demo PRD 里重复定义枚举全集 |
| 状态机、系统流程、幂等、补偿、推送重试 | 应用设计 / 流程设计 / 系统机制 | PRD 落到操作规则、验收标准和页面状态展示 | 页面按旧状态口径自行展示 |
| 页面布局、控件、交互反馈、Mock 展示 | Demo PRD / 界面设计 / 前端规范 | 前端原型按此实现 | 用 Demo PRD 反向修改业务规则 |
| REST 路径、DDL、索引、错误码、部署 | 技术设计 | PM 文档只记录必要业务约束 | 技术实现细节写入 PM PRD |

> [!NOTE]
> 数据设计中的枚举是业务概念层枚举，用来解释业务语义；字段清单中的枚举是页面和接口字段的展示/输入权威来源。两者冲突时，先回到业务规则确认，再同步更新字段清单，不允许各写一套。

### 3.4 变更回扫机制

ERP 文档最容易出问题的不是初稿，而是后续局部变更后旧口径残留。因此凡涉及以下变更，必须执行全链路回扫：

| 变更类型 | 必扫文档 |
| --- | --- |
| 单据废止 / 链路替换 | 需求设计、业务架构、业务用例、数据设计、应用架构、状态机、系统机制、系统用例、PRD、Demo PRD、Mock |
| 状态枚举 / 状态模型变化 | 数据设计、应用设计状态机、字段清单、业务 PRD、Demo PRD、前端 Badge / 操作矩阵 |
| 字段新增 / 删除 / 改名 | 字段清单、业务 PRD、Demo PRD、导入导出、Mock、前端表单和详情 |
| 价税 / 金额 / 数量规则变化 | 全局规范、字段清单、业务 PRD、应用机制、Demo PRD、计算示例、Mock |
| 外部系统交互变化 | 应用架构、系统机制、系统用例、流程推演、PRD、测试验收标准 |

**回扫完成标准**：旧口径不能只在文档顶部声明废止，正文、流程图、用例、字段表、示例、Mock 都必须同步处理；确需保留历史说法时，必须标明"历史稿 / 已废止 / 仅供溯源"。

## 四、四种设计的核心对比

| 维度 | 需求设计 | 业务设计 | 应用设计 | 技术设计 |
| --- | --- | --- | --- | --- |
| **谁主导** | 产品经理 | 产品经理 | 产品经理 | 研发/架构师 |
| **站的视角** | 用户/干系人 | 客户/业务方 | 用户 + 系统 | 技术实现方 |
| **核心问题** | 系统必须做什么 | 业务应该怎么做 | 系统怎么做才好用 | 技术上怎么实现 |
| **关键词** | 正确性、完整性 | 业务价值、流程优化 | 易用性、应变性 | 可行性、可维护性 |
| **典型产出** | 需求规格说明书 | 流程图、数据设计文档 | 界面原型、应用架构 | 接口文档、DDL |

## 五、常见混淆问题解答

### Q1：应用设计和业务设计边界在哪里？

- **业务设计**：说清楚"业务是怎么跑的"，关注流程和规则是否正确
- **应用设计**：说清楚"系统是怎么实现的"，关注组件和机制是否好用

两者的分界线：一条流程图如果是在描述业务现实（谁做了什么），属于业务设计；如果是在描述系统行为（系统如何响应用户操作），属于应用设计。

### Q2：技术设计和应用设计的边界在哪里？

| 内容 | 属于哪个层次 |
| --- | --- |
| 界面原型、交互规范 | 应用设计 |
| 状态机、应用架构图 | 应用设计 |
| ER 图（逻辑数据模型） | 应用设计（偏技术边界） |
| 数据库 DDL、索引设计 | 技术设计 |
| 接口文档（具体字段/协议） | 技术设计 |
| 部署架构、性能优化方案 | 技术设计 |

### Q3：后台产品需要特别注意什么？

相比 to-C 产品，中后台/ERP 系统产品经理必须额外关注：

- **性能与稳定性**：大数据量下的响应速度、并发处理能力
- **扩展性**：业务规则变化时系统能否灵活配置，不需要大改代码
- **错误与逆向机制**：操作失败怎么处理、数据错了怎么修正（红冲/取消/关闭的逻辑）
- **工程化产出**：需要输出用例、流程图、原型等可被测试和运维参考的文档

### Q4：需求设计、业务设计、应用设计和 PRD 怎么避免重复？

用"问题粒度"区分，而不是用文件名区分：

| 层次 | 回答的问题 | 粒度 |
| --- | --- | --- |
| 需求设计 | 要解决什么问题，做什么，不做什么，优先级是什么 | 范围级、功能点级 |
| 业务设计 | 业务应该怎么跑，规则是否正确，异常怎么闭环 | 业务步骤级、规则级 |
| 应用设计 | 系统怎么承接业务，状态怎么流转，机制怎么复用 | 系统行为级、机制级 |
| PRD | 研发和测试具体按什么做、按什么验 | 字段级、操作级、验收级 |

如果同一段内容在多个文档中重复出现，必须指定一个权威源，其他文档改成引用或摘要。

### Q5：这套方法论和敏捷、DDD、传统 PRD 流程是什么关系？

| 方法论/框架 | 与本方法论的关系 |
| --- | --- |
| **传统 PRD 流程**（需求 → PRD → 开发） | 本方法论是在传统流程的"需求"和"PRD"之间插入了业务设计和应用设计两个细化层。对于简单项目，传统流程完全够用；对于复杂后台系统，两个中间层的价值是填平"需求说不清、PRD 写不全"的鸿沟。 |
| **用户故事地图**（User Story Mapping） | 用户故事地图解决的是"需求怎么组织和排期"的问题，对应本方法论的需求设计层；它不涉及业务规则推演和系统机制设计，所以不能替代业务设计和应用设计。两者可以互补：故事地图作为需求设计的工具之一，三层设计作为后续深化的框架。 |
| **DDD 限界上下文** | DDD 的限界上下文和本方法论的应用架构设计有很强的对应关系——两者都在解决"系统模块边界怎么划"的问题。DDD 更偏向技术侧的领域建模，本方法论更偏向业务侧的组织与流程建模。实践中可以结合使用：业务设计的业务架构对应 DDD 的业务领域识别，应用设计的应用架构对应 DDD 的限界上下文划分。 |
| **事件风暴**（Event Storming） | 事件风暴是发现业务流程和业务规则的优秀方法，可以作为业务设计阶段"流程推演"的启动工具。事件风暴产出的事件和命令，与本方法论流程模型的步骤和触发条件有自然对应。 |
| **敏捷迭代** | 三层设计不要求一次性瀑布式完成全部设计再进入开发。每个迭代内，可以先做该迭代范围内功能的轻量三层设计，再进入该迭代的 PRD 和开发。三层是"分析深度"，不是"阶段锁定"。 |

> [!NOTE]
> 本方法论不排斥任何具体工具或框架。需求调研可以用用户访谈、问卷、竞品分析等各种手段；流程建模可以用 Mermaid、泳道图、事件风暴；原型可以用 Figma、Axure、甚至手绘线框图。方法论定义的是**分析层次和产出结构**，不是具体的工具选择。

## 六、ERP 重构中产品经理的 AI 协作实践指南

> 本章是基于书中方法论的实践延伸，结合 AI IDE 的实际协作经验整理，供产品经理在 ERP 重构项目中参考。

### 6.1 哪些设计是产品经理必须亲自完成的？

**必须亲自把关的内容**：

| 阶段 | 必须产出 | 原因 |
| --- | --- | --- |
| **需求设计** | 访谈结论、需求优先级裁定 | AI 无法替你判断"哪个需求更重要" |
| **业务设计** | 业务规则的最终确认、流程推演 | 只有产品经理理解业务语义，AI 无法判断业务是否正确 |
| **应用设计** | 单据定义、状态机、功能清单+优先级 | 这是业务逻辑转化为系统设计的关键桥梁，必须产品经理把关 |

**可以让 AI 辅助或生成初稿的内容**：

| 内容 | AI 可以帮忙做什么 | 产品经理需要做什么 |
| --- | --- | --- |
| 流程推演文档 | 根据业务背景生成详细流程、补充异常分支 | 提供业务背景，确认逻辑是否正确 |
| ER图、状态机 | 生成 ER 图、状态机、联动规则表的结构化初稿 | 确认与实际业务规则一致 |
| PRD 字段清单 | 生成字段初稿（类型、必填、校验规则） | 逐项确认是否符合业务要求 |

### 6.2 哪些内容放在 AI IDE 里？

AI IDE 的核心价值：**让 AI 在工作时有完整上下文，能做出贴合业务的高质量输出**。

**必须放在 IDE 的内容（AI 的"长期记忆"）**：

```
项目根目录/
├── 全局背景信息/           ← 系统定义、组织架构、通用规范（喂给 AI 的长期背景；无固定模板，需根据项目上下文动态添加和持续维护）
├── 需求设计/               ← 需求规格说明书、业务/功能需求一览表（含优先级）
├── 业务设计/               ← 按「产出物类型」组织，而非按业务模块
│   ├── 业务架构/           ← 组织架构图、业务流程总览、权限模型
│   ├── 流程模型/           ← 各业务场景的详细流程图（含正常/取消/异常分支）
│   ├── 数据设计/           ← 业务实体关系、术语、业务概念枚举、业务规则索引
│   └── 业务用例/           ← 描述"谁做了什么"的业务用例文档
├── 应用设计/               ← 按「产出物类型」组织，而非按模块/功能
│   ├── 应用架构/           ← 系统应用层架构图、组件划分与调用关系
│   ├── 流程设计/           ← 业务流程拆解到可编码粒度的流程分解图
│   ├── 系统机制/           ← 权限体系、审批流、配置管理、日志、通知等横切机制
│   ├── 界面设计/           ← 高保真原型、交互规范、UI 设计系统
│   └── 系统用例/           ← 应用层用例（描述系统与用户的交互行为）
├── PRD/                    ← 独立存放；综合三层设计，面向研发/测试的可交付文档
└── AGENTS.md               ← 项目规则和踩坑记录
```

> [!NOTE]
> **全局背景信息/ 的说明**：这是一个动态维护的文件夹，不是固定模板的目录。里面存放的是项目启动时需要喂给 AI 的上下文信息，例如：系统定义（这个系统是做什么的）、组织架构（涉及哪些集团/部门/角色）、通用规范（编码规则、命名约定、全局业务约束等）。内容根据项目实际情况自由增删，不需要参照固定模板。关键是**经常维护**——项目每进入一个新阶段，全局背景信息就要同步更新，确保 AI 始终基于最新上下文工作。

> [!NOTE]
> **两个设计层都按产出物类型归档，而非按业务模块**：这样无论系统做什么业务，文件夹结构都保持稳定，不会因为"这次是ERP、下次是CRM"而需要重新设计目录。

---

**各目录内容说明**：

**业务设计层**

| 目录 | 存放什么 | 典型形式 |
| --- | --- | --- |
| 业务架构/ | 系统的业务全貌：组织有哪些角色、哪些部门、权责是什么，从宏观视角交代清楚"生意是怎么做的" | 组织架构图、业务总流程图 |
| 流程模型/ | 每个具体业务场景的完整流程，要覆盖正常流程、取消/撤回、异常处理等各种分支 | Mermaid 流程图、时序图 |
| 数据设计/ | 业务上有哪些核心概念（实体）、它们之间是什么关系（概念 ER 图）；统一业务术语定义和枚举值清单，避免研发、产品、业务方三方对同一个词有不同理解 | 概念ER图、实体关系说明、术语表、枚举值清单 |
| 业务用例/ | 从用户视角描述"谁在什么情况下做了什么"，有助于澄清系统边界和角色职责 | 用例说明文档或用例图 |

**应用设计层**

| 目录 | 存放什么 | 典型形式 |
| --- | --- | --- |
| 应用架构/ | 系统由哪些应用模块组成、模块之间如何调用、数据如何流转；是系统的"骨架图" | 应用架构图、模块依赖图 |
| 流程设计/ | 把业务流程"翻译"为系统操作步骤，细化到用户点了什么按钮、系统做了什么响应 | 系统交互流程图、状态机 |
| 系统机制/ | 权限、审批、配置、日志等"横切关注点"的统一设计方案，这些机制会被多个功能模块共用 | 机制说明文档、规则表 |
| 界面设计/ | 高保真界面原型和交互规范，通常在 Figma/Axure 中维护，此处可只放链接或关键截图说明 | 原型链接、交互规范文档 |
| 系统用例/ | 从系统视角描述"系统与用户如何交互"，比业务用例更贴近实现，包含界面操作的前置/后置条件 | 系统用例说明文档 |


**不需要常驻 产品经理的IDE 的内容**：
- 技术设计文档（DDL、接口文档）——研发侧产物，可以放在技术的文档中或者是团队项目文件中
- 原型截图——可以单独放在原型链接中，例如Figma、Axure等
- 会议纪要——存储在在线文档或者会议软件中即可

### 6.3 三阶段 AI 协作模式

| 阶段 | 你做什么 | AI 做什么 | 关键原则 |
| --- | --- | --- | --- |
| **业务设计** | 与业务方沟通，确认业务规则 | 整理成结构化流程推演文档 | AI 产出必须经过业务审核 |
| **应用设计** | 确定功能范围、提供业务规则、审核设计方案 | 生成架构图、状态机、流程分解图、系统用例初稿 | 逐条确认每个设计决策 |
| **PRD 输出** | 确定功能边界、字段约束、验收标准 | 生成 PRD 正文、字段清单、交互规则 | 验收标准必须你来定，AI 只负责格式化 |

### 6.4 什么不能交给 AI？

1. **业务规则的最终裁定**：ERP 业务逻辑有行业特殊性，AI 无法判断"这个规则是否合理"
2. **跨业务的优先级决策**：做不做、先做哪个，是产品策略判断
3. **边界情况的业务确认**：异常分支的处理方式，答案必须来自业务方
4. **评审共识**：设计文档需经评审，AI 生成的初稿不能绕过评审直接交付

> [!IMPORTANT]
> **核心结论**：AI 最大的价值是把产品经理从"把想清楚的东西写清楚"中解放出来，让你有更多时间"把事情想清楚"。**想的部分不能省，写的部分可以让 AI 帮你。**

### 6.5 AI 协作的阶段门禁

AI 生成或改写文档前，先判断当前处于哪个阶段，并按对应门禁检查。不满足门禁时，先补前置文档，不要直接写 PRD 或原型。

| 阶段 | 进入下一阶段前必须确认 |
| --- | --- |
| 需求设计 → 业务设计 | 范围、Out of Scope、优先级、关键干系人、外部系统依赖已明确 |
| 业务设计 → 应用设计 | 正常流程、取消/撤回、关闭/终止、红冲/修正、异常分支已覆盖；核心业务规则有编号和来源 |
| 应用设计 → PRD | 应用架构、状态模型、系统机制、权限边界、幂等/补偿、外部系统交互已明确 |
| PRD → Demo PRD / 前端原型 | 字段清单已冻结；枚举、必填、展示、导入导出、操作矩阵已对齐 |

### 6.6 旧稿与迁移稿管理

历史文档可以保留，但必须降低误导风险：

| 场景 | 处理方式 |
| --- | --- |
| 旧稿已被正式 PRD 替代 | 文档头部标注"历史稿，仅供溯源，权威稿见..." |
| 部分章节仍有参考价值 | 在章节前标注"仅历史背景有效，业务规则以最新 PRD 为准" |
| 单据或流程已废止 | 正文必须同步删除或改写旧链路，不能只在标题或顶部声明废止 |
| AI 接手旧目录 | 先读 README / 索引 / AGENTS.md 的权威源说明，再检索正文，避免被旧文件名带偏 |
