# 生成原型标注

> **适用场景**：已有前端原型和 PRD 套件，用 `vitamin-prototype-annotation` 给页面挂只读业务标注。  
> **读者**：站在原型前看角标 /「本页规则」的人（产品、研发、测试、业务），不是 PRD 作者自己。  
> **写法样板（必须对齐）**：`prd-docs/跨境电商ERP/设置/用户与角色/annotations/pages/`  
> skill 已把同一套标准写入 `references/writing-standard.md`：**之后每次使用该 skill，都按本目录现有标注输出**，不要退回进销存采购订单那种内部编号体。  
> 先读样板里的 `user-role-global.md`、任意一页列表/表单/详情（如 `user-list.md`、`user-form.md`、`role-detail.md`），再写本次标注。旧进销存采购订单等标注偏内部编号、规范码和路由字面量，**不要学那套口气**。

把下面「提示词」里的花括号换成本次模块信息后发给 Agent。

---

## 提示词

```text
请使用 vitamin-prototype-annotation，为下面模块生成或更新原型标注。

前端原型目录：{原型工程路径}
PRD 资料目录：{该模块 PRD 套件路径}
写法样板：prd-docs/跨境电商ERP/设置/用户与角色/annotations/pages/
标注覆盖页面：
1. {列表页}
2. {新增页}
3. {编辑页}
4. {详情页}
（按实际页面增删，例如配置权限、分配等独立页也要列入）

═══════════════════════════════════════
一、先做流程，再写说明
═══════════════════════════════════════

先检查真实路由、页面定位和已有标注；已有则增量更新，保留稳定 id 和无关内容。
读取主 PRD、字段清单和对应 Demo 版 PRD，提取各页关键规则及交互约束。
模块跨列表、新增、编辑、详情共用的背景与链路、业务场景、状态机、动作矩阵、核心规则、权限与校验，默认写成 type 为 global 的跨页规则，用 routeMatcher 覆盖该模块全部相关路由，并加入 workspace。各页 page-global 只保留该页特有规则，不把跨页规则留空。
每条规则能回溯到来源文件和章节；资料冲突或未定义的内容单列「待确认」，不编造。
更新标注 Markdown 和必要配置；尚未接入时按现有工程完成接入。
不要为挂标注重构业务组件或改变页面布局，不同页面的规则不得混显。
完成后编译标注包，列出修改文件、覆盖区域、待确认项和实际检查结果。

═══════════════════════════════════════
二、写法标准（比流程更重要：读者必须看得懂）
═══════════════════════════════════════

标注是「对着屏幕讲清楚」的说明，不是 PRD 摘要，也不是研发内部备忘。
请按写法样板重写，不要整段粘贴主 PRD，不要用采购订单旧标注那种编号体。

1. 先说人话，再说约束
   - 每个块开头用一两句讲清：这是哪、谁在用、要达成什么。
   - 跨页「模块背景」必须回答「为什么要有这个模块」「本期做 / 明确不做」「模块怎么理解」。
   - 跨页「业务场景」用表：场景 | 谁在做 | 要达成什么。不要写 S01、主流程/支线 这种内部编号当主文。

2. 表格优先，少写长段落
   - 字段、按钮、查询项、校验、状态能不能点，一律用表。
   - 字段表至少能看懂：字段名、新增/编辑是否可改、是否必填、一句话规则。
   - 按钮表至少能看懂：按钮名、何时显示、点了去哪或发生什么、成功/失败用户看到什么。
   - 关键限制加粗：保存后不可改、不提供删除、不在本页改状态、本页不配置某能力。

3. 用页面中文名，不用实现字面量当正文
   - 读者说明里写「回到角色列表」「进入编辑用户」，不要把 #/settings/...、DRAFT、VISIBLE 当成主句。
   - 枚举码、规范编号（如 V-PO-xxx、G-PHONE-REGEX、R12）、需求 ID 不要写进读者主文；来源用书名号和章节，例如「主 PRD §六」。
   - 路由、选择器、blockId 只放 config / 技术核对，不塞进角标正文。

4. 写清「本页做什么 / 不做什么」
   - 列表页：入口菜单、有没有保存、Tab/查询/行操作怎么配合。
   - 新增编辑：保存成功去哪、失败是否留下、状态/权限等是否「不在本页改」。
   - 详情：只读、无保存、改资料/改权限分别去哪。
   - 本页不展示的字段或能力要点名（例如「启停不在本表单改，去列表或详情点按钮」）。

5. 用户能看见的反馈必须写原文
   - 校验：什么情况、标在哪个字段/区域、提示原文。
   - 成功/失败 Toast、二次确认文案、离开未保存确认文案，有则照抄，无则标「待确认」。
   - 不要只写「见 §6.1 宽松校验」却不复述规则本身。

6. 状态与动作要对着按钮讲
   - 状态机用中文状态名 + mermaid；动作表写「允许 / 不允许」，或「当前为启用时显示停用」。
   - 不可用操作写清是「不显示」还是「显示但点了被拦截」。
   - 状态变更只能通过动作按钮，与 AGENTS.md 一致。

7. 待确认单独成句
   - 已确认规则和待确认不要混在同一单元格里当已定论。
   - 原型和 PRD 冲突时列出双方原文，不擅自选边。

═══════════════════════════════════════
三、各页建议块（按真实 UI 裁剪，不要为凑块而空挂）
═══════════════════════════════════════

跨页 global（单独 md + config）：
- 模块背景与链路
- 业务场景
- 状态与流转
- 列表里能点哪些操作（或动作能力）
- 核心业务规则
- 谁能进这个模块、出错怎么提示

各页 page-global：只写本页入口、模式、保存/离开、本页明确不做的事。

列表页 element 通常按：状态 Tab → 查询区 → 工具条 → 表格与行操作。
新增/编辑页通常按：表单字段分组 → 子表/明细 → 底栏与校验。
详情页通常按：页头与操作 → 信息卡片 → 只读明细/权限快照 → 系统信息或日志入口。

═══════════════════════════════════════
四、写完自检（不过不交付）
═══════════════════════════════════════

1. 没读过本模块 PRD 的人，只看标注能否独立操作：从哪进、能改什么、不能改什么、点完去哪、失败看到哪句文案。
2. 正文里没有成段的规范编号、枚举码、hash 路由、场景 ID。
3. 跨页规则在模块内至少两个页面都能读到，且没有串到其他模块。
4. 各页 page-global 没有复述整份状态机；整份 PRD 没有塞进 global。
5. 口气和信息密度对齐写法样板，而不是旧采购订单标注。
```
